# 233固件集成计划

## 当前完成范围

- 工程正式命名为 **233固件**，仓库目录 `233-firmware`。
- PAXX develop 源码、完整 Git 提交历史及其 screen-apps 子模块已拉取；主仓库使用按需获取历史文件内容的 partial clone。
- multiACE 源码及 Git 历史已拉取，子模块固定在与 PAXX managed 包匹配的 v1.27b；main 的 1.50-pre 代码保留为后续评估来源。
- 项目元数据和构建入口使用 `2.1.0-233-dev.1` 与 `U1_233_..._upgrade.bin` 命名。
- 本次没有运行完整固件构建、修改打印机配置、刷机、推送仓库或发布固件。

## 下一步重构顺序

1. **统一打包**：研究 `providers/multiACE/multiace/managed/` 的包生成接口，将指定本地源码构建为 managed 包，记录 SHA-256，让固件安装的内容与 233 仓库固定的源码一致。决定依赖随镜像提供还是首次启动安装，并补齐包验证与版本记录。
2. **统一生命周期**：沿用 PAXX 的组件选择、服务、Klipper overlay mount、持久配置目录、权限与恢复入口。保持一个运行中的 ACE provider，避免独立安装器、自更新器和固件管理器同时修改同一套文件。
3. **统一品牌与界面**：在 233 自有元数据、版本显示及发布产物中使用“233固件”，保留上游作者与来源说明。再整理中文界面、ACE—耗材—喷头拓扑及设备详情。屏幕应用和 Helix UI 作为单独变更评估。
4. **接入已验证功能**：评估并迁移当前工作区的中文界面和按每圈出料长度估算余量的工具，继续处理 RFID 诊断中发现的待修问题；先区分已验证代码、测试工具和未完成的实现，不把示例、缓存字段或配置关系当成实测状态。
5. **验证与产物**：依次做静态检查、managed 包验证、镜像构建、解包核对版本与组件、设备启动及 ACE 实机回归，再形成可发布版本。每项分别记录源码提交、固件 SHA-256、嵌入版本和实际硬件结果。

## 当前集成边界

PAXX 已有 `extended-multiace` profile，定义在 `overlays/mods/multiace/`；本次复用它，不重复另建 ACE 安装系统。

但该 profile 的 multiACE 是运行时按需下载、按 SHA-256 验证的发布包。目前的本地 provider 子模块是供后续重构使用的源码，尚未替换该发布包入口。因此“源码已准备”“镜像构建成功”“233 本地 provider 已集成”“设备已通过测试”是四个分别需要验证的状态。

## 初始化时发现的上游工作区问题

multiACE 的 README 在提交中使用 CRLF，但 `.gitattributes` 要求 LF，刚克隆就会显示 README 被修改并阻止切换版本。已确认工作区文件与提交原始字节完全一致后，仅在该子模块的本地 Git `info/attributes` 中为 `README.md` 设置 `-text`，以保留上游字节并切到固定版本；没有修改全局 Git 配置或上游源码。
